# Roadmap

Directional only. Nothing here is a commitment to build, maintain, or deliver.

## Under Consideration

**Additional regional overlays.** `reference/regional-overlays.md` covers EU and MENA. APAC, LATAM, and Sub-Saharan Africa would follow the same pattern: procurement platforms, company registries, statistics bureaus, standards and regulatory databases, plus the region-specific guardrails. Each overlay is a research project, not a template fill.

**A win/loss skill.** The HUMINT sweep ends by generating interview questions and raising a gap flag, because public signals infer why deals move and only interviews know. The interview synthesis itself is currently out of scope, and every build-signal story in this library is capped because of it.

**A positioning-statement handoff.** `reference/frameworks.md` describes the say-versus-said-about gap as positioning raw material and hands it off. There is no skill here that writes the statement.

**Worked examples using a single continuous case.** Several examples already share the fictional Cartelane engagement. Extending that consistently across all twenty-two would let a reader follow one investigation from routing through monitoring.

## Long-Term: Thematic GitHub Projects

There is no active GitHub Project board and no plan to create a general-purpose backlog. If a board is opened in the future, it should support one bounded theme with a clear research or contribution question. It should close when that theme has produced its intended learning or artifacts.

Possible themes include:

**Domain-specific extensions.** Explore how the collection disciplines change in a particular industry or domain: which public sources matter, which inference chains fail, which terminology needs an overlay, and which guardrails are specific to that setting. The result might be a reference overlay, a taxonomy, or a small number of additions to existing skills. It should not become a parallel library by default.

**Public practice and failure studies.** Study well-known, publicly documented company practices to understand why a market-intelligence method worked or failed. This theme requires an explicit governance decision before launch. Under the current Constitution, the Project cannot become a store of real competitive research or named-company dossiers. Sources must be public and rights-clear, and the durable contribution may need to be a method-level finding, a citation list, or a synthetic teaching example rather than the company research itself.

**Cross-domain method research.** Compare how practitioners in product management, product marketing, pricing, sales enablement, market research, and competitive intelligence make the same judgment call. The output should sharpen doctrine, weak examples, or violation signals rather than merely collect opinions.

A thematic Project should not be created until it has all of the following:

1. One named question and a boundary for what will not be studied
2. A contribution format that prevents live findings, confidential material, and client information from entering a public surface
3. A named moderator and the same variable-response expectation used by this Project
4. A defined destination for the result: an issue, reference update, synthetic example, or deliberately separate publication
5. A closing condition, so the board does not become a permanent implied commitment

These are long-term possibilities, not scheduled work.

## Deliberately Out of Scope

**Anything that collects for you.** These are instructional materials describing a method. They are not a data service, and the Project stores no competitive research about any real company.

**A utility tier.** Precedents Thinking caps its supporting utilities at six so the method stays findable. This Project takes the stricter position: every skill collects for a named discipline, fuses named disciplines, consumes fused evidence into a named artifact, or diffs a named prior run. Nothing else earns a place. See the contribution test in `CONTRIBUTING.md`.

**Paid-source integrations.** The reference material names paid tools where they exist, because knowing what you are not buying is useful. Building against them is not.

**A permanent GitHub Project backlog.** A board without a bounded theme would imply ongoing delivery and maintenance. Issues and pull requests are enough for concrete improvements to the current library.
